# 05 · 家庭场景与 MVP

> Current status (2026-11): inventory, recipes, weekly menu, meal records, and shopping list are working manually; assistant runtime and proactive reminders are next. See README and [`12-assistant-architecture.md`](12-assistant-architecture.md).

> 这个项目首先是一个**自己家会真的用**的产品；架构是手段，不是目的。
> 目标不是做企业平台，而是：一个人能维护、AI 能帮忙、家里用得上、以后还能长出新东西。

---

## 1. 一天 / 一周的真实场景

| 场景 | 现在的麻烦 | 项目怎么帮 | 用到的模块 |
|---|---|---|---|
| 早上：“今晚吃什么？” | 想不出来，最后重复那几样 | 按库存 + 家人口味 + 时间，给 2–3 个建议 | recipe、meal_plan |
| 下班：“冰箱还有什么？” | 忘了买过什么、有没有过期 | 库存/位置/保质期一眼看到 | inventory、catalog |
| 买菜前：“这周缺什么？” | 临时想、漏买、重复买 | 从一周菜单生成采购清单，合并同类项 | meal_plan、shopping list |
| 收纳：“东西放哪了？” | 翻箱倒柜 | 物品 + 位置 + 照片 | inventory、intake |
| 拍照：“小票/食材入库” | 手动录入烦 | 拍照 → 识别草稿 → 人确认 → 入库 | intake、inventory |
| 育儿/养花/健康：“这正常吗？” | 搜一堆广告/焦虑 | 带出处、低置信拒答的知识问答 | knowledge |
| 家务：“该做的事老忘” | 靠脑子记 | 待办/提醒，可由菜单/库存触发 | task |
| 家庭记忆：“想留点东西” | 照片散落 | 以后做时间线/月报（不急着做） | journal（未来） |

**优先级**：先把“库存 → 菜谱 → 一周菜单 → 采购清单”跑通；这是家里每周都会发生的事。

---

## 2. MVP：一条真正的闭环

### “这周吃什么 + 缺什么”

```text
物品/库存
  → 菜谱（家里常做的 10–20 道就够）
  → 一周菜单（早/午/晚，可留空）
  → 采购清单（按库存扣减、合并同类项）
  → 低库存 / 临期提醒
```

**第一版只做这一条闭环**：

- 物品：名称、分类、位置、单位、数量/批次、保质期。
- 库存：入库/出库/调整，保留流水，当前数量算出来。
- 菜谱：标题、食材、步骤、份数；先不做营养计算。
- 菜单：按周排；可以手动改；不追求“智能推荐”。
- 采购：从菜单生成，合并相同物品；可勾选。
- 快速录入：一行输入/最少字段，记住上次位置和单位；先规则，不接 AI。
- Web：能完成上面所有操作，手机上也能用。

**先不做**：多用户、权限、移动 App、复杂推荐、营养分析、价格/预算、社交分享。

> **实施提醒**：P1 只启动 `home-web` + `home-core` + PG；`home-ai` 到 P3 再起。两个 schema 如果配置摩擦大，先用一个 schema + 表前缀，等 AI 服务真正上线再拆；边界靠模块和 role，不靠 schema 数量。

### 成功标准（家庭尺度，不是企业指标）

- 家里真的用它排过一周菜单，并按清单买过菜。
- 库存数量基本可信；临期能看到。
- 新增一件物品可以“几秒内完成”，不是每次都走完整表单。
- 生成菜单/清单不超过 1 分钟（人工可改）。
- 家人愿意用第二次。
- 出问题能恢复：备份/恢复演练做过一次。

## 3. 后续可以长出来的东西（按模块加，不重写）

| 想法 | 怎么做 | 什么时候 |
|---|---|---|
| 拍照入库 | `intake`：图片 → 草稿 → 确认 → 库存 | P3 |
| 家庭知识库 | `knowledge`：育儿/食材/养花单域，引用+拒答 | P4 |
| 自然语言入口 | `agent` + `tools`：pi-agent 识别意图，查库存/建待办 | P5 |
| 植物养护 | `plants` 模块 + `task` 提醒 + `knowledge` 问答 | 以后 |
| 家庭月报/记忆 | `journal` / `reporting`：照片、事件、统计 | 以后 |
| 家庭预算 | `budget`：采购花费、月度汇总 | 以后 |
| 家务分工 | `chores`：任务 + 成员（到时有用户再说） | 以后 |
| 家庭“今晚吃什么”投票 | `meal_plan` + 简单页面 | 以后 |

**关键**：每个想法都是一个新模块或一个 feature；不改现有模块的 domain。这样想象力不会把系统撑爆。

## 4. AI 机会与边界

### 适合 AI 的

- 图片/小票 → 结构化草稿（人确认后入库）。
- 按库存/口味/时间给菜谱建议。
- 知识问答：带出处、低置信拒答。
- 自然语言入口：“记一下牛奶快没了”“今晚吃什么”。

### 不适合 AI 的

- 精确库存/金额/日期：以数据库为准，不让模型“猜”。
- 高风险医疗/育儿判断：只给带出处的信息，建议就医。
- 不可逆操作：删除、批量覆盖、外发消息，必须人确认。
- 没有真实数据时的“智能推荐”：先把菜谱和库存做出来。

## 5. 主动不做（anti-enterprise）

| 不做 | 原因 |
|---|---|
| 多租户 / SaaS / 计费 / 开放注册 | 自己家不需要；会拖慢闭环 |
| RBAC / OIDC / JWT / 用户表 | Phase 1 局域网/VPN + 共享 token 够用 |
| K8s / 服务网格 / 事件总线 / API Gateway / LLM Gateway | 3 个容器 + 1 个 PG 够用；有真实需求再加 |
| 正式审批流 / SLA / on-call / 大规模观测 | 家庭级 best effort；先做备份/恢复 |
| 一开始就十几个模块 | 先 3–4 个业务模块，按场景长 |
| 移动 App / 小程序（第一版） | 响应式 Web 先跑通；真有需要再说 |

> 这些不是“做不到”，是**当前约束下不划算**。代价是少一些企业能力；收益是能把时间花在真实闭环上。

---

## 6. 这个项目想证明什么

1. **能在约束下做减法**：不是堆技术，而是选 3 个程序、1 个库、1 个写入口。
2. **能设计数据边界**：库存流水、草稿/确认、只读知识，谁写什么很清楚。
3. **能判断 AI 的边界**：什么时候用 AI、什么时候用 SQL/表单、什么时候不上 Agent。
4. **能一个人 + AI 持续交付**：模块模板、检查清单、先跑通再抽象。
5. **能承认代价**：少一些企业能力，换更快的真实使用和更低的维护成本。
