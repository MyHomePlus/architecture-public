# 04 · 设计亮点与取舍

> 这不是功能清单，而是这个架构里几个“为什么这样选”的关键决定。
> 状态：v0.2；P2.4 厨房 Web 已跑通手工版；助手 runtime 仍是设计态。没有实测的数字不写。

---

## 1. 三个程序，不是六个服务

**问题**：资源、拍照识别、知识、助手看起来是四块，很容易拆成 4 个服务 + 网关 + 4 个库。

**选择**：只保留 3 个程序：

- `home-web`：界面
- `home-core`：Django，业务真相源
- `home-ai`：FastAPI，感知、AI 能力、未来助手/技能

**代价**：AI 依赖都在一个镜像里；模块之间靠纪律，不靠网络边界。

**收益**：少两个服务的部署/联调/监控；一个人 + AI 能同时 hold 住。

图：[`01-overall`](../diagrams/01-overall.puml)

---

## 2. 库存只有一条流水

**问题**：直接改“当前数量”很爽，但改错了不知道改了什么，也没法回滚。

**选择**：库存只追加流水（入库/出库/调整/过期），当前数量 = 流水求和；批次单独记，用于保质期。

**代价**：写多一条流水；查当前数量要聚合/投影；不能随手改历史。

**收益**：可追溯、可冲正、可重算；以后做临期/低库存不用再补审计。

图：[`05-data-ownership`](../diagrams/05-data-ownership.puml)

---

## 3. AI 只交草稿，人确认才入库

**问题**：拍照识别一定会错；如果识别完直接写库存，错一次就要手工擦屁股，还可能重复写。

**选择**：感知/AI 只产出草稿或待确认 action；人确认/修正后，才经 core API 提交；提交带幂等键。

**代价**：多一步确认；低置信时要人改。

**收益**：AI 出错不污染真相；重复提交不会重复写；以后可以换模型/provider。

图：[`04-write-path`](../diagrams/04-write-path.puml)

---

## 4. 层叠式：能力 → 服务 → 技能 → 助手

**问题**：原来的图分散在部署、模块、数据、写入路径，工程上完整，但很难讲清“这个助手到底怎么来的”。

**选择**：

```text
L5  领域助手       库存 / 吃饭 / 采购 / 提醒
L4  生活技能       每个技能只属于一个助手
L3  领域服务       读共享，写只写自己
L2  原子能力       OCR/ASR / LLM / 规则 / 调度 / 通知
L1  能力基座       3 个程序 / 1 个 PG / 文件 / jobs
```

层叠图是**组合视图**，不是部署图；工程细节仍看模块/数据/写入/部署图。

图：[`00-layered-overview`](../diagrams/00-layered-overview.puml)

## 5. 领域助手隔离，数据底层共享

**问题**：一个“全知 Assistant”很容易把所有工具、所有上下文、所有写权限都揽过来，最后既难解释也难控。

**选择**：

- 库存 / 吃饭 / 采购 / 提醒四个领域助手；
- 助手之间**不互调**；
- 不共享会话/上下文/工具白名单；
- 可以经 domain read contract 读共享数据；
- 写只写自己的业务域；
- 首页可以聚合卡片，但那是 UI 聚合，不是助手互相感知；
- 跨域动作由用户切换助手，暂不做隐式编排。

**代价**：有些“一句话跨多个域”的体验要拆成两步；需要设计共享读契约。

**收益**：上下文更小、权限更窄、责任更清楚；不会长成不可解释的 god assistant。

图：[`12-assistant-architecture`](12-assistant-architecture.md)

## 6. 先固定流程，再谈多 Agent / 编排

**问题**：很容易一上来就 LangGraph/多 Agent/审批/checkpoint，结果没有真实多步任务，全是空转。

**选择**：

- 当前用固定流程 + 单步工具 + 草稿确认；
- 规则优先，LLM 只做抽取/解释/偏好收窄；
- 真实多步任务出现前，不做 `agent_runtime`；
- 不做多 Agent 协作。

**代价**：现在不能自动完成复杂多步任务；有些事要人点几下。

**收益**：入口轻、延迟低；工具/业务不被 Agent 框架绑死；以后加编排不改现有模块。

---

## 7. 家庭吃饭：多菜、确认、可追溯

**问题**：家庭一餐不是“一道菜”；计划也不等于实际吃了什么。

**选择**：

- 周菜单是一周的聚合，一餐多菜；
- 确认前任意一天可改；确认后只读；
- 确认后生成不可变 `meal_record`，带 `dish_index`、食材快照、来源；
- 采购清单是独立动态清单，不从库存扣减、不自动入库。

**代价**：JSONB 周数据要服务层校验；确认后修正要走新记录。

**收益**：符合家庭真实吃饭；计划/实际/采购三者边界清楚。

图：[`10-scenario-weekly-menu`](../diagrams/10-scenario-weekly-menu.puml)

---

## 8. 旧菜谱导入：先保留，再判断

**问题**：旧 stash-spot 有 37 道菜谱，但没有步骤，也没有任何“做过”的可靠记录。

**选择**：

- 导入 37 道菜谱 / 249 条食材；
- 分类映射为 tags；
- 难度/时间/旧 id 写入 notes；
- 步骤为空就保持为空；
- 不伪造“做过”标签；等用户提供名单再标。

**代价**：这些菜谱可用于推荐/采购，但不能直接当做法教程。

**收益**：旧数据先保住；不把“菜谱库里有”误当成“真的做过”。

## 这套项目想证明什么

1. **能在约束下做减法**：3 个程序、1 个库、1 个写入口；主动不做微服务/网关/消息队列。
2. **能设计数据边界**：库存流水、草稿/确认、知识只读、采购与库存解耦。
3. **能判断 AI 的边界**：能用 SQL/表单的不用模型；能固定流程的不上编排；AI 只提案，人确认。
4. **能做领域隔离**：四个助手各管一域，不互相感知；共享数据但不共享上下文。
5. **能承认代价**：少一些企业能力（多租户/RBAC/K8s/事件总线），换更快的真实使用和更低的维护成本；这是选择，不是做不到。
